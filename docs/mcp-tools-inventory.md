# MCP tools inventory (SCRUM-75), 28 Sep 2026

Every tool the MCP server (`/mcp`, `src/lib/mcp/index.ts`) exposes, what it reads or changes,
and what stops a user from seeing more than they should. The OAuth side (tokens, consent,
revocation) is covered in `docs/mcp-oauth-review.md` (SCRUM-59). `src/lib/__tests__/mcp-inventory.test.ts`
checks this table against the code: a new tool, or a tool touching a new table, fails CI until
this file is updated.

## How every tool call is protected

1. **Token.** A Supabase access token for a signed-in user, checked for issuer and audience by `@lovable.dev/mcp-js`.
   This covers both entry points: `/mcp` (JSON-RPC) and `/.mcp/invoke-tool/<tool>` (REST, generated by
   the SDK and using the same authorizer).
2. **Revocation.** `withAudit` (`src/lib/mcp/audit.ts`) refuses the call if the user disconnected this client,
   and also refuses when that check can't be completed (fail closed, #29).
3. **Row access.** Queries run with the **caller's own token** (`supabaseForUser`, publishable key). RLS
   decides which rows come back, exactly as in the web app. No tool uses the service role.
4. **Audit.** Every call writes a row to `mcp_tool_audit_log` with the user, client, tool, arguments
   (strings capped at 500 chars), success, error and duration. Users read their own rows and admins read
   all (MCP audit page); updates and deletes are blocked.
5. **Errors.** Database errors reach the AI client as a friendly message plus a ref, never raw (#29).

## Tools

| Tool | Class | Inputs | Output | Tables read | Permission check | Risk / follow-up |
|---|---|---|---|---|---|---|
| `whoami` | read | none | user id, email, roles | `user_roles` | Token; RLS: own roles only | none |
| `list_customers` | read | `search` (name substring), `limit` ≤ 200 | active customers: id, name, account manager, industry, active flag | `customers` | Token; RLS: any role can read customers | Customer list goes to an external AI client; acceptable for roled users |
| `list_transactions` | read | `customer_id`, `lab_type`, `cloud_provider`, `line_of_business`, `start_date_from/to`, `limit` ≤ 200 | transaction lines incl. **`selling_cost` and `input_cost`** | `transactions` | Token; RLS: any role can read transactions | **Finance fields go to every role incl. viewer: SCRUM-58** (Vivek's matrix) |
| `reports_summary` | read | `year`, `cloud_provider`, `line_of_business` | totals: transactions, users, **revenue, input cost, profit, margin %** | `transactions` (all matching rows, #16) | Token; RLS: any role can read transactions | **Same finance exposure: SCRUM-58** |

Summary: **4 tools, all read-only, none write or delete.** Each declares `readOnlyHint: true`, and the
server only sends SELECT queries, under the caller's RLS.

Each call also writes (not a tool):

| What | Table | Written by | Notes |
|---|---|---|---|
| Audit row per call | `mcp_tool_audit_log` | the user's own token (policy "insert own") | Append-only. A user could add extra audit rows **about themselves** through the API. That doesn't hide anything, but see SCRUM-77 |
| Revocation check | `mcp_revoked_clients` (read) | – | Disconnect/undo from the Agent integrations page |

## Follow-ups

| Item | Ticket | Status |
|---|---|---|
| Cost/revenue/margin visible to every role through `list_transactions` / `reports_summary` | SCRUM-58 | Waits on the finance visibility matrix (Vivek) |
| Audit rows written with the user's token (forgeable for oneself); audit retention not defined | SCRUM-77 | Open. Retention needs a decision |
| Any future **write** tool must: add a role check on the server, require an explicit confirm like the AI Command Center (#26), and be added here as `write` or `destructive` | – | Rule; the test fails if a tool drops `readOnlyHint` |

The AI Command Center is not part of the MCP server. Its write actions (Freshdesk proposals) and
their confirmation/role rules are in `docs/ai-command-center.md` (SCRUM-76).
